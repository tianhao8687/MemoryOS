# DeepSeek V4 Flash 中等任务 MemoryOS A/B/C 试验报告

结论：这一轮不能证明 MemoryOS 提高中等编程任务的完成率，但它证明了一个更局部的信号：记忆能让 Flash 更少地搜索仓库并更早找到正确修复边界，其中渐进式 C 同时降低了输入 token 和费用。但 A/B/C 全部在真正编辑前被共同的 no-patch 门槛停止，所以对端到端“有没有用”必须判为不确定。

## 试验设计

- 真实任务：Pylint `pylint-pr-6528`，修复递归发现对 `--ignore` / `--ignore-patterns` / `--ignore-paths` 的语义。
- A = `no_memory`；B = `msc_full`；C = `msc_progressive`。
- 同一模型、提示、起始 commit、运行时、隐藏测试和请求上限。首请求的 system/messages/generation 哈希相同，只有预期中的 MemoryOS 工具 schema 不同。
- 随机冻结顺序：B → C → A；每组仅一次；供应商重试为 0。
- 模型：`deepseek-v4-flash`；Harness `0.1.0-rc.5`；MemoryOS 插件 `0.1.6`。

## 结果

| 指标 | A 无记忆 | B 完整 | C 渐进 |
|---|---:|---:|---:|
| 隐藏测试 | 失败 | 失败 | 失败 |
| 补丁 | 0 bytes | 0 bytes | 0 bytes |
| 发起尝试 / 完整响应 | 9 / 8 | 9 / 8 | 9 / 8 |
| 输入 token | 122,123 | 99,591 | 92,133 |
| cache-miss token | 16,651 | 16,519 | 10,981 |
| cache-hit token | 105,472 | 83,072 | 81,152 |
| 输出 token | 1,497 | 3,959 | 3,050 |
| 已完成响应精确费用 | $0.0030456 | $0.0036538 | $0.0026186 |
| 整轮延迟 | 121.96 s | 141.34 s | 132.55 s |
| MemoryOS 调用 | 0 | 1 context | 1 context + 1 explain |
| 仓库工具调用 | 13 | 11 | 11 |
| 形成正确诊断前的仓库调用 | 9 | 6 | 5 |

相比 A：

- B 输入 token 下降 18.45%，诊断前仓库调用下降 33.33%；但因长推理输出，费用上升 19.97%，整轮延迟上升 15.89%。
- C 输入 token 下降 24.56%，cache-miss 输入下降 34.05%，已完成响应费用下降 14.02%，诊断前仓库调用下降 44.44%；整轮延迟上升 8.68%。
- C 在本轮的效率指标上明显优于 B，但两者都没有产生补丁。

三组合计 27 次 pre-dispatch 尝试、24 次有完整 usage 的供应商响应，合计 313,847 输入 token、8,506 输出 token，精确已完成响应费用 $0.0093179688。每组第 9 次尝试在发送前钩子记录后被异步预算轮询终止；供应商可能看到了这 3 个请求，但没有返回 usage，因此不在精确 token/费用总数中。

## 为什么没成功

不是插件没有调用。B/C 都成功收到了与任务直接相关的正确记忆：共享一个 ignore 判定，保留 basename/path 语义，并在 yield 或下降之前剪掉忽略目录。B 和 C 都在第 6 个响应形成这个诊断，A 在第 7 个响应形成。

共同失败点是控制器与预设不匹配：为了让 B/C 都能运行，本轮用了通用 `standard-offline` 预设，它没有“形成明确编辑方案后立即编辑”的截止规则。三组在已理解问题后仍继续查文档、测试和历史，然后在 8 个完整响应时被 no-patch 门槛停止。C 被取消的第 9 个响应甚至正在准备再做两次 grep，还不是编辑。

因此，不能把这次简化为“题目太难”，也不能说“插件调用失败”。轨迹更支持：Flash 在这道中等题上能理解修复，但当前通用预设没有把它从调研推到编辑。

## 应该如何解读

- 可以说：MemoryOS 在本任务上提供了正确上下文，并减少了定位所需的仓库探索；C 还减少了输入 token 和费用。
- 不能说：MemoryOS 已经提高了中等任务的修复成功率。
- B 的完整模式在这一样本上输出过长，费用反而更高；C 是下一轮更值得保留的实验组。

## 下一轮先修什么

1. 做一个任务无关、同时支持 A/B/C 的 coding 预设，三组共享同一编辑规则。
2. 一旦能说出具体 patch，下一次工具调用必须编辑；最晚在第 6 次仓库检查后开始编辑。MemoryOS 调用不算仓库检查。
3. 可以适度放宽 no-patch 上限，但它只是保险丝，不能代替编辑截止规则。
4. 把请求上限改为同步 pre-dispatch 拦截，避免每组最后一个被取消请求到达服务器。

本报告没有自动重跑，也没有加题。
