# DeepSeek V4 Flash × MemoryOS 插件 A/B/C 报告（live-r2）

生成日期：2026-08-17（Asia/Shanghai）  
运行 ID：`medium-abc-v2-live-r2`

## 结论

这轮优化严格发生在 MemoryOS 插件侧，没有给 DeepSeek Agent 加入“第六次调用后必须写代码”、编辑期限或其他针对模型行为的提示。A、B、C 使用相同的 `standard-offline` Agent 预设、任务提示、模型、推理等级、代码起点和并行启动条件。

插件优化有两个已被本轮数据支持的效果：

1. C 的模型可见接口开销下降。C 相对 B 的增量 schema/wrapper 开销由旧版的 546 bytes 降为 350 bytes，减少 196 bytes（35.9%）。前三个请求累计输入 token 中，C 为 24,005，B 为 24,068；即使 C 多调用了一次 `memory_explain`，仍少 63 token。
2. C 更早形成了正确的问题诊断。本题轨迹中，C 在第 5 个响应明确定位核心契约，B 在第 7 个，A 在第 10 个。这只是单题信号，不能外推为稳定成功率提升。

但本轮没有证明插件提高修复成功率：A、B、C 最终补丁均为空，隐藏验收均失败。C 在定位后产生了较长的继续推理，没有进入编辑；其输出 token 和费用显著增加，最终被 130% 相对费用保护器拦截。因此当前最准确的判断是：**插件压缩与诊断辅助有效，但端到端修复收益尚未成立，C 的整轮成本效率本题不合格。**

## 实验控制

- 任务：`pytest-pr-10356`，中等难度，修复 pytest 多继承类的 mark/MRO 查找与去重。
- A：`no_memory`，不暴露 MemoryOS 工具。
- B：`msc_full`，完整 JSON MemoryOS 上下文。
- C：`msc_progressive`，优化后的渐进式紧凑 MemoryOS 接口。
- 模型：`deepseek-v4-flash`；推理等级：`high`。
- Agent：三个方案均为 `standard-offline`。
- 提示词 SHA-256：三个方案均为 `31d3141dbd8a4f35a99698ea079d1e3598f8b6a10ed12ebacd6d0b904a38d017`。
- Provider 重试：0；三个方案同时运行；没有自动重复或自动扩容。
- 隐藏补丁与评分工作区位于三个 Agent 工作区之外，Agent 无法读取隐藏验收内容。
- 保护规则：当另外两个方案都结束后，若未结束方案的输入 token、Provider 尝试数或费用超过两者最大值的 130%，在下一次 Provider 请求发出前停止。

## 插件侧改动

1. 新增 `deepseek-progressive-compact` 返回格式：`memory_context` 返回精简的纯文本项目索引，并移除 UUID、来源与记账等不影响模型决策的易变元数据。
2. 保留 `memory_explain` 渐进取证能力，但参数由四项缩减为一个精确的 `UUID @ SHA256` 句柄；解释结果只保留事实、证据与新鲜度。
3. 插件在 Provider 请求记账和发送之前同步检查控制器写入的用量保护文件，触发后保留现有补丁并进入一次隔离评分。
4. 插件版本提升至 `0.1.8`，并补充紧凑协议与请求前保护器的契约测试。

第 3 项属于测试安全能力，不计作 MemoryOS 检索质量收益。隐藏评分隔离和三臂监控属于评测基础设施，不计作插件功能收益。

## 紧凑协议的直接证据

- 旧版预检首请求：A 32,580 bytes，B 32,775 bytes，C 33,321 bytes；旧版 C 相对 B 增量为 546 bytes。
- 本轮首请求：A 32,596 bytes，B 32,791 bytes，C 33,141 bytes；新版 C 相对 B 增量为 350 bytes。
- C 相对 B 的接口增量减少 196 bytes，即 35.9%。
- 本轮前三个请求总字节数：B 102,745，C 102,628；C 少 117 bytes。
- 本轮前三个请求总输入 token：B 24,068，C 24,005；C 少 63 token。

这说明紧凑协议确实抵消了 C 额外一次渐进解释调用的早期输入开销。C 的最终高费用并非由紧凑返回载荷造成，而是第 5 和第 9 个响应出现了很长的模型推理输出。

## 130% 保护器行为

保护器做出决定时，A 与 B 已结束；C 当时为 10 次尝试、9 个完成响应、130,212 输入 token、费用 USD 0.0049744912。B 是同伴最高费用，为 USD 0.0029100064；130% 上限为 USD 0.00378300832，因此保护器写入停止决定。

C 的第 10 个请求当时已经在途，返回后最终费用上升到 USD 0.0053381888。插件随后在下一次发送前拦截，未记录第 11 次 Provider 尝试。也就是说，保护器能保证“不再发下一次请求”，但无法撤回已经在途的响应；本轮确实出现了一次在途超调。

## 为什么不能规定“第六次就开始写”

轨迹没有给出固定步数的依据：同一题中正确诊断分别出现在 A 的第 10、B 的第 7、C 的第 5 个响应。真正可观察到的问题是三个方案在诊断后都继续调查而未编辑，不是“第六步”这个数字本身。把固定编辑期限写进 Agent 提示会改变被测 Agent，并把结果污染成针对 DeepSeek V4 Flash 的行为特调，所以本轮没有这样做。

工具轨迹也支持这一点：A 使用 `read×7 / grep×6 / bash×3`，B 使用 `memory_context×1 / read×5 / grep×3 / bash×2 / glob×1`，C 使用 `memory_context×1 / memory_explain×1 / read×8 / grep×4 / bash×1`；三者均没有编辑操作。

## 验收结论边界

- 已证明：插件安装和调用链可用；完整与渐进工具均被 Agent 实际调用；紧凑协议降低接口开销；渐进记忆在本题更早提供正确契约；隐藏评分隔离有效；130% 请求前保护有效。
- 未证明：修复成功率提高；总 token 稳定下降；总费用下降；跨题泛化；C 优于 B 的端到端成功率。
- 本轮否定：C 在本题的整轮成本效率不优于 A/B；C 费用比 B 高 83.4%，比 A 高约 93.0%。
